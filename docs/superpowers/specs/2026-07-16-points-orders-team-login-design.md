# 积分、订单、团队币消息与登录能力收敛设计

## 背景

项目当前正式版本为 `0.2.5`，后端健康接口运行在 Direct 模式。此次设计基于实际代码、活跃 SQLite 数据库、远端只读接口、App 数据库样本和 APK 反编译结果，不依赖猜测。

已确认的问题如下：

1. 账户升级进度原始数据包含正确的 `progressPointTotal=5000`，但前端会在缺少显式总值时错误地把 `historyPoint` 当作目标值，导致显示为 `3178.2 / 3178.2`。
2. 面板订单历史只查询本地 `point_store_orders`。远端只读接口 `/pointstore/order/list` 能返回 App 中的历史订单，因此多数账号的旧订单没有进入面板。
3. 正式直连团队消息会丢弃正文为空、币数只存在于 `msgMeta` 的 531/532 消息，也不能完整解析 3300 common-event 的 `args.params`。
4. 手动会话导入已经可用；手机号验证码、邮箱密码和手机号密码虽然有界面与路由骨架，但 Direct 登录核心未完成，不应继续作为正常可选项展示。

## 目标

1. 正确展示账户升级进度和目标积分。
2. 同步远端商城历史订单，与本地订单审计记录安全合并。
3. 修复说道币、叮咚币到账与兑换团队消息的正式直连解析。
4. 收敛登录页面，只展示当前真正可用的登录方式，并优化手动会话导入体验。
5. 修正订单状态在网页和 Telegram 通知中的显示。
6. 正式部署继续完全脱离模拟器；模拟器只用于逆向和测试取证。

## 非目标

- 本次不实现尚未掌握完整 Direct 协议的邮箱密码、手机号密码或手机号验证码首次登录。
- 不实现 WeChat、Facebook、Google、Apple 或 AccountKit 登录。
- 不发送团队币消息到面板通知或 Telegram。
- 不调用商城兑换接口进行验收，不产生扣积分操作。
- 不依靠 ADB、App 数据库或模拟器完成正式消息接收。
- 不删除远端本次未返回的本地订单或历史消息。

## 方案选择

采用“按需远端同步 + 本地缓存合并”方案。

打开账号的订单历史时，后端读取远端订单列表，规范化后按账号和远端订单 ID 写入本地缓存，再与本地下单审计记录合并返回。远端不可用时继续返回本地缓存并标记数据可能陈旧。该方案比纯实时展示更可靠，也比后台定时全量同步的改动和远端压力更小。

## 升级进度设计

后端序列化账户快照时明确输出 `progress_point_total`。数据优先级为：

1. 远端明确返回的 `progressPointTotal` 或同义字段。
2. 已验证的会员等级目标映射，例如 V4 对应 5000。
3. 无法确定时返回空值。

`historyPoint`、`validPoint` 和当前进度不得作为目标总值。前端展示规则为：

- 已知总值：`当前进度 / 目标总值`。
- 未知总值：`当前进度 / -`。
- 不再使用当前进度填充目标值。

本项不需要数据库迁移。

## 商城历史订单设计

### 数据流

```text
前端打开订单历史
  -> 账户订单 API
  -> 获取或复用 point-store 用户标识
  -> GET /pointstore/order/list
  -> 规范化远端字段与状态
  -> 按 accountId + remoteOrderId upsert
  -> 与本地审计订单合并
  -> 按实际兑换时间倒序返回
```

### 合并规则

- 远端订单按现有唯一关系 `(accountId, remoteOrderId)` 更新或创建。
- 本地 `submitting`、`unknown`、`failed` 等审计记录即使不在远端列表中也必须保留。
- 不因一次远端列表缺项删除本地记录。
- 同一订单优先使用远端返回的状态、商品信息和实际兑换时间。
- 商品图片、名称、积分成本和接收邮箱只保存现有业务所需字段。
- 页面和日志中的邮箱必须脱敏；Token 和完整远端请求上下文不得写入日志。

### 状态规范化

在现有状态基础上增加：

```text
4 -> processing / 进行中
5 -> completed / 已完成
```

Telegram 对状态 4 使用“订单处理中”，对状态 5 使用“兑换成功”。未知数字状态保留为 `unknown`，并保存原始状态用于诊断。

### 错误处理

- 远端成功：返回最新合并结果和刷新时间。
- 远端失败且有缓存：返回缓存，并设置 `stale=true` 和安全的错误摘要。
- 远端失败且无缓存：返回空列表和明确的同步失败状态，不伪装成“没有订单”。
- 单个异常订单不能导致整批订单同步失败。

## 团队币消息设计

### 直连规范化

`normalizeDirectWebOfflineMessages` 必须保留与 App 等价的消息 envelope，并支持：

- 外层类型 3300。
- 内层 `msgMeta.k1` 为 531 或 532。
- 数字发送方但会话或元数据能够确认属于团队秘书消息。
- 标题和正文为空、有效信息只存在于 `msgMeta` 的消息。

合法币消息不能因为空标题或空正文被丢弃。规范化后的消息类型优先使用内层 `k1`，同时保留原始元数据到受控字段。

### 内容提取

运行时解析同时读取：

- 正文 envelope 中的 `msgMeta`。
- `row.data2`。
- common-event 的 `args` 和 `args.params`。

生成用户可读的中文正文，例如：

- `任务完成，获得 20.00 说道币`
- `兑换成功，20.00 说道币已到账`
- `获得 20.00 叮咚币`

币名称根据账号应用类型确定。原始 JSON 不在页面展示。

### 去重更新

同一 `msgId` 重新扫描到更完整数据时，允许更新正文、发送方和 `k5Flag`，把旧的泛化 3300 记录升级为正确的 531/532 记录。普通短信和 type 29 offer 的既有分类不能受到影响。

团队消息继续只存入对应账号内部，不进入面板通知，不发送 Telegram。

## 登录能力设计

账号新增页面默认只提供：

- 邮箱 + 验证码。
- 手动导入直连会话。

手机号验证码、邮箱密码和手机号密码暂不作为可选方式展示。数据库中已经存在的其它 `loginType` 数据不会被修改或删除，导入和兼容逻辑继续保留。

手动会话导入需要：

- 对用户 ID、Token、设备 ID 和应用类型提供清晰说明。
- Token 使用敏感输入控件，默认隐藏。
- 导入前调用现有 Direct 校验。
- 对失效 Token、用户不匹配、设备参数缺失和远端超时给出可理解的错误提示。
- 校验失败时不启用监听。

## 前端交互

### 账户详情

- 升级卡片显示明确总值或 `-`。
- 保持现有会员、余额和积分卡片布局。

### 订单历史

- 打开历史订单时自动同步一次。
- 提供手动刷新按钮、刷新中状态和最近同步时间。
- 展示商品、消耗积分、兑换时间、状态、脱敏邮箱和数据来源。
- 区分“确实没有订单”“当前显示缓存”和“同步失败且无缓存”。
- 使用实际兑换时间倒序，不使用批量导入时间排序。

### 团队消息

- 页面只展示规范化后的正文和现有时间、来源信息。
- 不显示原始元数据 JSON。

### 登录页面

- 不再让用户选择尚未真正可用的登录方式。
- 手动会话输入提供显示/隐藏 Token、字段说明、校验进度和明确结果。

## 测试策略

所有功能先增加失败测试，再实现代码。

### 升级进度

- 显式 `progressPointTotal=5000` 优先。
- V4 且缺少显式总值时推导为 5000。
- `historyPoint=3178.2` 永远不能成为目标值。
- 无可验证目标时返回空值，前端显示 `-`。

### 订单同步

- 解析远端 `data` 数组和字段变体。
- 状态 4/5 正确规范化。
- 远端历史与本地下单记录正确合并且不重复。
- 远端缺项不删除本地审计记录。
- 单条异常数据不影响其它订单。
- 远端失败时返回缓存和陈旧标记。
- 按远端实际兑换时间倒序。
- Telegram 状态 5 标题为“兑换成功”。

### 团队币消息

- 531/532 空标题、空正文、只有 `msgMeta`。
- 数字发送方币消息。
- 3300 + `args.params.credits`。
- TalkU 和 DingDong 两种币名称。
- 同 `msgId` 泛化旧记录升级。
- type 29 非团队 offer 仍被排除。
- `normalizeDirectWebOfflineMessages -> storeHelperSmsMessages` 端到端回归。

### 登录和前端结构

- 登录选项只包含真实可用方式。
- 手动会话 Token 使用敏感输入控件。
- 订单同步状态、空状态和标签结构存在。
- 账户升级目标不会回退到 `historyPoint`。

## 验收

1. 后端完整测试通过。
2. 后端 TypeScript 生产构建通过。
3. 前端生产构建通过。
4. 实际账户升级进度显示正确。
5. 使用只读远端列表同步历史订单，确认 App 截图中的脱敏样本能够出现。
6. 不调用订单创建或兑换接口。
7. 正式 Direct 链路可解析团队币消息，运行时不依赖模拟器。
8. 健康接口、监听状态、Git 状态和敏感信息检查通过。

## 发布与安全

本设计检查点版本提升到 `0.2.6`。后续实现提交继续遵守“每次新提交提升版本号”的项目规则；如推送前需要保持远端单个脱敏提交，再单独执行本地提交压缩和最终版本核对。

提交或推送前继续检查：

- `.env` 和数据库文件。
- Token、密码和完整邮箱。
- 手机号、设备标识、局域网地址。
- 日志、抓包文件和逆向临时产物。

正式部署只运行后端、前端和数据库服务，不依赖模拟器或 ADB。
