# v0.2.10 Direct 短信监听恢复设计

## 背景与证据

v0.2.9 运行实例中 9 个监听账户均显示 `online/running`，但实例启动后没有新增消息，也没有收到任何 `0x0103` 短信帧。两个 Direct 网关仍有大量 `0x0102` 和未知帧，但配对注册、registered link 读取持续在数秒内被远端断开并重连。

资源边界计数显示 raw/JSON 队列丢弃、超大帧和 socket buffer 溢出均为 0，因此当前证据不支持“16MB/8MB 队列上限直接丢短信”。本次修复聚焦 Direct 已认证连接的生命周期和监听健康状态。

## 目标

- 恢复不依赖 App、helper 或模拟器的 Direct 实时短信接收。
- 保留等待器泄漏修复、队列字节上限、缓存上限和并发治理。
- 避免已认证 push/link socket 因空闲读暂停而进入高频断线重连。
- 底层持续失败时不再向面板报告正常监听。
- 发布版本升级为 0.2.10。

## 非目标

- 不重新启用正式部署的 App/helper/ADB fallback。
- 不整体回滚 v0.2.9 的资源治理。
- 不改短信解析、跨账户目标号码路由和 Telegram 通知规则，除非真实 `0x0103` 已到达后发现独立问题。

## 方案

### 1. 连接读循环

移除已认证 Direct socket 的 `socket.pause()` / 定时 `resume()` 空闲节流。非短信日志和处理循环仍使用已有批次、事件循环让出和日志节流，防止 CPU 忙循环。

等待器超时后仍必须精确移除，不能恢复旧的泄漏行为；短信帧仍保持最高队列优先级，raw 16MB、JSON 8MB 总预算保持不变。

### 2. 监听健康状态

监听诊断继续记录每个主机的连接尝试、重连和最近错误。当两个配对网关在一个监听窗口内持续无法维持注册连接、且没有有效 push 路径时，本轮监听返回失败，由现有有界退避重试；面板不得长期保持无错误的假在线状态。

短暂单次断线仍按可恢复错误处理，不把账户标记为登录失效。

### 3. A/B 验证

先以测试覆盖证明：没有等待器时连续非短信帧不会暂停底层 socket；日志节流和帧批处理仍生效。实现后重启本地 0.2.10，观察已知账户的连接持续时间、重连频率和 `offlineCatchupSends` 增长速度。

真实短信验收必须出现完整链路：网关收到 `0x0103`、解析出短信、写入数据库，并按账户设置触发 Telegram。至少使用一个此前成功的英国或荷兰号码；法国线路不作为唯一验收号码。

## 测试与验收

- 新增失败测试，覆盖“空闲非短信帧不得暂停已认证 socket”。
- 新增监听健康测试，覆盖持续配对失败不能报告健康运行。
- Direct 相关测试、后端完整测试和 TypeScript 构建全部通过。
- 指定账户 459 Direct regression 全部通过。
- 本地停止/启动后无残留进程，health 版本为 0.2.10。
- 运行指标中队列丢弃和超大帧计数无异常。
- 真实已知成功号码至少收到一条短信；若仍没有 `0x0103`，保留诊断证据并停止继续叠加修复。

## 回滚条件

如果取消 socket 读暂停后连接仍以相同频率断开，立即撤销该行为修改，转而对配对注册所有权和 link 重建流程做下一轮单变量排查，不恢复旧等待器泄漏，也不启用生产模拟器兜底。
