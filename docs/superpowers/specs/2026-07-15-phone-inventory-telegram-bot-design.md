# 全局手机号管理与 Telegram 机器人交互优化设计

## 背景

当前项目版本为 `0.2.4`。实际运行环境健康接口返回 `gatewayMode=direct`，工作树在设计开始前保持干净。当前活跃 SQLite 数据库为 `backend/prisma/prisma/dev.db`，其中有 29 个已购手机号，全部处于 `active` 状态，分布在 9 个账户中。号码记录的国家码、Provider、购买类型、支付类型、有效期、获得时间、到期时间和原始数据均已落库，多数号码也有备注。

现有网页只在单个账户详情内展示手机号，缺少跨账户的统一视图。现有 Telegram Bot 已支持账户、号码、消息、监听、通知、刷新、购号和号码生命周期命令，也有基础按钮面板，但菜单层级较浅、消息会不断新增、全局手机号入口缺失，安全操作与危险操作没有形成清晰的交互分层。

## 目标

1. 新增全局手机号管理页面，以账户为一级分组展示所有已购号码。
2. 明确展示号码来源账户，并支持直接跳转账户详情。
3. 提供搜索、筛选、复制、修改备注、单账户刷新和确认后的全量刷新。
4. 将 Telegram Bot 调整为按钮优先、命令保留的分层交互。
5. 优化 Telegram 消息结构、排版、错误提示和按钮操作过程。
6. 保持现有短信监听、团队消息隔离、Direct 网关和危险操作确认机制不变。
7. 完成功能后统一提升版本到 `0.2.5`。

## 非目标

- 不在全局手机号页面提供续费、暂停、恢复、取消或购号操作。
- 不把购号、续费、暂停、恢复和取消加入 Telegram 按钮菜单。
- 不新增 Telegram 会话状态表或其他数据库迁移。
- 不改变短信解析、消息入库、主备网关协调或账户监听协议。
- 不依赖模拟器运行正式功能；模拟器仅继续用于逆向和测试。

## 方案选择

采用按功能拆分的实现方式：新增独立的手机号资产路由和服务，抽取可复用的号码同步逻辑；Telegram 保留现有轮询和权限校验入口，将菜单、回调解析和格式化拆成聚焦模块。该方案比继续扩展 `accounts.ts` 和 `telegram-bot.ts` 更容易测试和维护，同时避免引入统一任务引擎等超出本次目标的基础设施。

## 后端架构

### 手机号资产服务

新增独立服务负责：

- 从本地数据库查询手机号及其所属账户。
- 应用关键词、状态、国家码和 Provider 筛选。
- 按账户现有 `sortOrder` 排序并分组。
- 计算号码总数、正常号码数、所属账户数和即将到期数量。
- 从 `rawJson` 中安全提取套餐 ID、价格、区域等可选补充信息。
- 不向前端返回 Token、密码、设备标识或未经筛选的原始 JSON。

全局查询接口设计为：

```text
GET /api/phone-numbers
```

支持以下可选查询参数：

```text
keyword
status
country_code
provider_id
```

返回结构为：

```json
{
  "summary": {
    "total": 29,
    "active": 29,
    "account_count": 9,
    "expiring_soon": 0
  },
  "groups": [
    {
      "account": {
        "id": 433,
        "nickname": "账户名称",
        "app_variant": "dingtone",
        "status": "online",
        "monitor_enabled": true,
        "telegram_notify": true
      },
      "phones": []
    }
  ]
}
```

### 号码同步服务

将现有单账户号码同步逻辑抽取为共享服务，供以下入口共同使用：

- 现有 `POST /api/accounts/:id/phone-numbers/sync`
- 全局页面的单账户刷新
- 新增的全量刷新接口

全量刷新接口设计为：

```text
POST /api/phone-numbers/refresh-all
Body: { "confirm": true }
```

后端固定使用最多 2 个账户的并发度，避免同时对多个 Direct 会话施加瞬时压力。返回每个账户的 `success`、`failed` 或 `skipped` 结果。一个账户失败不得中断其他账户；没有有效 Direct 会话的账户记为 `skipped`。继续保持现有保守同步策略：远端本次未返回的本地号码不会被自动删除。

### 路由挂载

新增独立路由并通过现有鉴权中间件挂载：

```text
app.use("/api/phone-numbers", requireAuth, phoneNumbersRouter)
```

现有账户手机号接口路径和响应保持兼容。

## 前端页面设计

新增路由：

```text
/phone-numbers
```

左侧菜单增加“手机号管理”。页面采用用户确认的“按账户分组卡片”布局。

### 汇总与筛选

页面顶部显示：

- 号码总数
- 正常号码数
- 所属账户数
- 30 天内即将到期数量

筛选区域支持：

- 搜索手机号、号码备注、账户名称或账户 ID
- 按号码状态筛选
- 按国家码筛选
- 按 Provider 筛选
- 确认后的“刷新全部”

页面首次打开只读取本地数据库，不自动远程刷新，也不增加 SSE 或轮询。

### 账户分组卡片

账户卡片按现有账户排序展示。卡片头部包含：

- 账户名称和 ID
- 应用类型
- 账户在线状态
- 监听状态
- Telegram 通知状态
- 号码总数和正常号码数
- 跳转账户详情按钮
- 刷新该账户号码按钮

账户卡片支持折叠，便于账户数量增加后保持页面可读性。

### 号码内容

每个号码展示：

- 格式化手机号和复制按钮
- 号码备注
- 状态
- 国家码和 Provider
- 获得时间和到期时间
- 有效期天数
- 购买类型和支付类型
- 自动续费、主号码和靓号标记
- 短信接收开关
- 从原始数据安全提取的套餐 ID、价格、区域等补充信息

安全操作包括复制号码、修改备注、刷新所属账户和查看完整详情。修改备注继续复用现有号码备注接口。

## Telegram 机器人设计

### 模块边界

`telegram-bot.ts` 继续负责：

- 轮询更新
- 权限白名单校验
- 命令入口分发
- 回调入口分发
- 更新游标持久化

新增聚焦模块负责：

- 按钮菜单和分页键盘构建
- 回调数据编码与解析
- HTML 文本格式化与转义
- 账户、手机号、消息和状态视图的展示模型

### Telegram 发送能力

扩展 Telegram 服务以支持：

- `parse_mode=HTML`
- `editMessageText`
- 编辑失败时回退到 `sendMessage`

所有账户名称、号码备注和短信内容必须先进行 HTML 转义。消息统一经过长度限制，避免超过 Telegram 单条消息限制。

### 主面板层级

主面板按钮：

- 账户管理
- 手机号管理
- 最近短信
- 运行状态
- 命令帮助

账户列表和手机号列表均支持分页。回调数据采用短格式并保持在 Telegram 限制内，不新增服务端会话状态。

### 账户页面

账户详情展示：

- 账户名称和 ID
- 应用类型与在线状态
- 监听和 Telegram 通知状态
- 号码数与未读短信数
- 最近错误

安全按钮包括：

- 查看号码
- 查看最近短信
- 刷新资料
- 刷新号码
- 启动或停止监听
- 开启或关闭通知
- 返回账户列表或主面板

### 手机号页面

手机号入口先按账户展示号码数量，再进入号码列表和号码详情。手机号使用 `<code>` 标签显示，便于 Telegram 客户端复制。

号码详情可以展示备注、状态、国家、Provider、到期时间、自动续费和短信接收状态。“修改备注”按钮只生成可复制的 `/set_phone_note` 命令模板，不进入文本会话状态。

购号、续费、暂停、恢复和取消不提供按钮。原有命令及 `confirm` 机制保持不变，并在帮助中归入“高级危险操作”。

### 最近短信与通知排版

最近短信页面展示账户、目标号码、发送方、内容和接收时间。团队消息继续不进入面板通知，也不发送 Telegram。

短信通知统一为分段文本：

- 通知类型
- 账户
- 目标号码
- 发送方
- 验证码或短信内容
- 接收时间

错误信息转换为简洁中文，不返回堆栈、Token、密码、设备字段或底层请求参数。

### 交互过程

按钮点击后先确认回调。需要远程刷新的操作先编辑为“正在处理”，结束后在同一条消息更新结果。消息编辑失败时发送一条新消息作为兼容回退。原有命令保持向后兼容，`/help` 按查看类、安全操作类和高级危险操作类分组。

## 缓存与一致性

- 全局手机号查询使用独立缓存键。
- 修改备注、单账户刷新或全量刷新后失效全局手机号缓存及对应账户缓存。
- 页面不依赖消息 SSE，因为号码变化只来自明确的管理动作或账户刷新。
- Telegram 操作直接读取数据库最新值，执行修改后重新查询账户或号码状态再渲染按钮。

## 错误处理

- 查询接口失败时页面保留已加载内容并提供重试。
- 单账户刷新失败只在对应账户卡片显示错误。
- 全量刷新展示成功、失败和跳过的数量及逐账户原因。
- 修改备注失败时恢复原显示并提示原因。
- Telegram 回调解析失败时返回主面板，不执行任何真实操作。
- Telegram 编辑消息失败时回退为新消息。
- 所有远程操作继续使用现有超时和 Direct 会话校验。

## 测试策略

### 后端测试

先编写失败测试，再实现以下行为：

- 全局号码查询按账户排序并分组。
- 关键词、状态、国家码和 Provider 筛选。
- 汇总统计和 30 天到期统计。
- 原始数据补充字段提取与敏感字段排除。
- 全量刷新必须 `confirm=true`。
- 全量刷新并发上限为 2。
- 单账户失败不影响其他账户。
- 无 Direct 会话账户被标记为跳过。
- 远端遗漏号码不会删除本地记录。

### Telegram 测试

先编写失败测试，再实现以下行为：

- HTML 转义和长度限制。
- 回调编码、解析和分页。
- 主面板、账户、号码和消息按钮层级。
- 危险操作不会出现在按钮菜单。
- 原消息编辑成功路径。
- 编辑失败后的发送回退。
- 命令帮助分类和旧命令兼容。
- 团队消息不进入通知的既有回归保持通过。

### 前端与集成验证

项目当前没有独立前端测试框架，因此延续现有结构回归测试方式，先增加会失败的路由、菜单、接口调用和关键交互结构检查，再实现页面。完成后执行：

- 完整后端测试
- 后端 TypeScript 生产构建
- 前端 TypeScript 与 Vite 生产构建
- 直连协议回归
- 当前真实数据库页面验证
- 已配置 Telegram Bot 的真实菜单和排版验证

真实 Telegram 验证只执行查看、刷新、监听和通知开关等安全操作，不执行购号、续费、暂停、恢复或取消。

## 发布与安全检查

实现完成后版本统一提升至 `0.2.5`，同步检查 `VERSION`、前后端包版本、健康接口和现有发布文件中的版本引用。

提交或推送前检查：

- `.env`
- SQLite 数据库
- Token、密码和邮箱
- 手机号和账户敏感数据
- 日志、抓包和临时文件
- 设备标识和局域网信息

正式部署只使用后端、前端和数据库服务，不依赖模拟器。
